# Node.js 26移行・性能検証

この性能測定の時点では本番のNaveリンク、PM2、設定・台帳・SQLite・録画ファイルは変更していない。合成fixtureと隔離した/tmpで検証した。その後の本番切替は[移行実施記録](node26-cutover.md)を参照する。

## 測定条件と記録

A＝高速化前のローカルソース＋Node 24.22.2、B＝同じソース＋26.13.0、C＝高速化後＋26.13.0。各対象はウォームアップ2回、その後7回測定。件数1,000、辞書1,000作品／12,000話、TSは100,000パケット／18,800,000バイト、チャンク65,536バイト。文字列は主にASCIIの合成データで、実EPGの日本語比率を再現していない。入力・DBはスクリプトで生成し、本体の関数・録画一覧API・シリーズWorkerを呼ぶ。

測定は専用のローカルスクリプトと隔離した比較用ソースで実施しました。測定スクリプト、A/B/Cの生JSON、比較用patchはローカル検証資材であり、Git配布対象や製品の実行要件ではありません。この文書では測定条件と集計結果を記録します。

当時のローカル記録には、各サンプル、中央値、p95、min/max、CPU時間、RSS、イベントループ最大遅延、I/Oブロック数、出力ハッシュを保存しました。これらの資材の現在の存在や、配布版だけでの測定再実行は保証しません。

- peak RSSは処理単独の増分ではなくプロセス起動後の最高値。Workerも含み、対象間で累積する。
- I/Oブロック数はページキャッシュの影響を受け、論理バイト数ではない。
- イベントループ遅延は単体関数を直接呼んだ測定プロセスの値。Cleaner・シリーズは本番ではWorker内で動く。Operatorの停止時間・DROP率とは解釈しない。
- 同一マシンの隔離プロセスで測定した。実録画負荷、ストレージ待ち、ネットワークは再現していない。GC時間自体と実録画のDROPは未計測。
- 全7対象でA/B/Cの正規化済み出力ハッシュが一致。Cleanerは別途12条件で計画全体を比較し、時刻・処理時間以外が一致。TSは120条件で全フィールド一致。

## 結果

時間は中央値ms。B→Cは短縮率。対照測定の小差をソース改修の効果とは扱わない。

| 対象 | A：24 | B：26 | C：改修後26 | B→C | 扱い |
|---|---:|---:|---:|---:|---|
| JSON parse/stringify | 3.55 | 2.75 | 2.63 | +4.5% | 本体未変更・対照測定 |
| match主要計算 | 109.32 | 106.92 | 110.06 | -2.9% | 本体未変更・対照測定 |
| Cleaner索引・突合 | 1167.36 | 1068.11 | 20.73 | +98.1% | 採用 |
| シリーズ投影＋辞書検索20回 | 68.45 | 69.50 | 31.06 | +55.3% | 採用 |
| シリーズWorker起動・JSON転送 | 372.10 | 325.81 | 330.71 | -1.5% | 本体未変更・対照測定 |
| TS解析 18.8 MB | 17.41 | 16.49 | 10.60 | +35.7% | 採用 |
| 録画一覧API応答生成 | 2.40 | 2.22 | 2.25 | -1.3% | 本体未変更・対照測定 |

### 採用した変更

- Cleaner：競合パスとkey件数の全件走査を、同じ入力スナップショットから作る索引へ置換。ジョブ間で保存せず次回は最新台帳で再構築する。ロック、atomic保存、救済条件、ファイルアクセス範囲は維持。
- シリーズ検索：同じ辞書スナップショットのタイトル正規化結果をresolver内で保持。結果キャッシュは作らず、クエリーごとに順位・件数を計算する。辞書公開時は既存のresolver交換で破棄する。旧SQLite readerのinode固定も維持。
- TS：188バイトごとのBufferビュー生成をやめ、元Bufferとオフセットで読む。pendingは引き続きコピーして所有し、入力Bufferの後続変更に影響されない。同期回復・CC・TEI・カウンター・終了・backpressureは維持。

| 採用対象 | B CPU中央値ms | C CPU中央値ms | B loop最大ms | C loop最大ms |
|---|---:|---:|---:|---:|
| Cleaner索引・突合 | 1078.77 | 24.39 | 1155.53 | 36.14 |
| シリーズ投影＋辞書検索20回 | 76.74 | 36.45 | 86.18 | 36.54 |
| TS解析 18.8 MB | 24.78 | 18.88 | 21.77 | 17.66 |

TSの遅延はファイル全体をyieldなしで解析した値であり、録画中の1チャンクの遅延ではない。リアルタイムの改善率は未計測。

## Node 26の効果と変更しなかった箇所

- A（バージョンだけで得る効果）：compactなJSON parse/stringifyは今回A→Bで短縮した。全処理で速くなる保証はなく、生データの分布も参照する。
- B（26特有の機能を使う書き換え）：既存契約を維持して追加効果を示せる新APIへの置換は採用していない。
- C（thorn自身の改善）：上記3変更を採用。Operatorの後処理延期・直列キュー、Scheduler Worker、記録保存retry、match子プロセス、ffprobe・サムネイルとの排他は維持した。
- replacer/space付きJSON、stableJson、指紋・ハッシュの生成順序は変更していない。通常JSONと同じfast pathとは扱わない。
- シリーズWorkerのTextEncoderで専用ArrayBufferを作ってtransferする既存方式を維持。Buffer poolの転送や転送済みバッファの再使用は追加しない。
- SQLiteはprepared statement、transaction、Worker内同期処理、close後の原子的公開を維持。FS・HTTP・暗号・GCの未確認の高速化は主張しない。
- WUIは録画一覧GETの応答生成を測定。実HTTP・Socket.IO・ブラウザーの応答時間は含まない。録画ファイルへのstat等は追加していない。

## Installer負荷とソースビルド方針

公式バイナリ取得・展開を標準とし、取得／checksum／展開失敗でソースビルドへ進まない。installer node --allow-source-build、installer node-prepare 26.13.0 --allow-source-build、installer full --allow-source-build、upgrade --allow-source-buildでのみNaveの元のfallbackを許可する。Nave本体は改変せず、固定版のライブラリ関数を使う。

取得・展開・依存導入はnice +10／ionice idle、許可したソースビルドは並列数1。hard quotaではなく、録画への無影響を保証しない。準備用一時ファイルや起動後の旧依存削除も低優先度で行う。

隔離した実導入の実測（ネットワーク・ページキャッシュ依存、比較前に対する短縮率ではない）：

| 段階 | 経過秒 | CPU秒 | peak RSS KiB | input/output blocks |
|---|---:|---:|---:|---|
| 公式バイナリ取得 | 2.046 | 0.774 | 22,328 | 392 / 122,864 |
| 展開 | 1.519 | 1.873 | 11,816 | 0 / 460,728 |
| npm ci | 4.436 | 6.302 | 282,608 | 0 / 322,656 |
| npm lsによる検証 | 0.525 | 0.643 | 113,156 | 0 / 32 |
| node_modules publish | 0（秒単位） | 未計測 | 未計測 | 未計測 |

全段階のnice=10、依存導入・検証のionice=idleを確認。実ソースコンパイル、録画中の競合・DROP計測は実施していない。この測定時のnpm ci・置換はサービス停止後を想定した。現在はdependencies-prepareで停止前に隔離構築し、停止後にdependencies-publishで公開する経路もある。通常Upgradeの依存導入は停止後。停止前準備を近い予約だけで禁止しない。

## 移行・診断・受入

現在の移行先はNode.js 26.13.0です。Node 24の保持・バックアップ・復元・ロールバックは行いません。以下は手順の説明であり、この文書整理時に実機操作や再検証は行っていません。

1. 対象ユーザーとPM2管理先、録画中・直近予約、同じPM2管理先の他サービスを確認する。実機の停止・切替は承認された保守時間に行う。
2. `./chinachu installer node-prepare 26.13.0`でリンクを変えず準備する。公式バイナリを使えない場合だけ`--allow-source-build`を明示する。Upgradeでも同フラグはruntime修復・sudo・Node準備まで伝達される。
3. `./chinachu runtime-check`は読み取り専用。Root PM2の診断は明示的にsudoで実行する。exit 0＝検査範囲で問題なし、2＝要確認、1＝診断失敗。既存の`dump.pm2.bak`はPM2の保存fallbackとして確認するが、移行バックアップを新規生成しない。
4. 既存PM2管理先の修復には`sudo ./chinachu service runtime-repair local`または`root`を使う。同管理先のデーモン再構築は他アプリケーション・PM2モジュールにも一時停止・再起動が波及する。対象外サービスの明示的な旧24参照があれば名前・設定項目を報告し、その設定を無断変更しない。
5. Node/npmリンク、Chinachu/PM2設定、systemd、保存状態を26へ切り替え、旧24を削除してから26で起動・検証する。起動検証の成功を旧24削除条件にしない。saved-onlyは保存集合へ維持し、修復時に新たに起動しない。
6. `./chinachu upgrade`はGit更新より先に必要な実行環境の準備・修復・確認を行う。dirty treeや更新なしでも省略しない。PM2未登録時もNode/npm/依存を確認し旧24を削除するが、PM2は自動登録しない。
7. 起動・検証に失敗した場合は、報告された段階をNode 26側で修復する。旧24へ戻さず、台帳・録画履歴を古い状態で上書きしない。録画状態が不明なサービスを追加で停止しない。

[切替記録](node26-cutover.md)は中間段階の履歴です。旧24保持・退避物・当時の未検証事項を、現在の操作指示として使用しないでください。

## 当時の性能検証範囲

以下は性能測定時点の記録です。今回の移行処理整理後のテスト実績とは区別してください。

新規の恒久テスト4件は、診断・build許可・TS正確性・辞書索引の世代切替という独立した不足保証に限定した。既存Installer/Upgrade/Cleanerケースも維持・更新した。loopbackを使う4ファイルは作業ルールにより実行しない。独立サーバーや別ポートへ切り替えていない。これら録画/WUIテストはNode 26のCIで実行する必要があり、単体の成功を全体成功とは扱わない。

測定時に使用した/tmpのソース・合成fixtureは一時資材です。現在の存在は保証しません。Chinachu管理下の旧Node 24は、上記の移行工程で削除します。システムNodeは変更対象外です。
